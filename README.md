# Verdi NPI Port Trace

This tool uses Verdi NPI L1 Tcl APIs to trace driver/load relationships for all
instances of a Verilog module from an elaborated Verdi/VCS KDB.

The recommended input is a VCS/Verdi generated KDB:

```bash
./npi_trace.sh \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -module ysyx_22050058_pht \
  > pht_trace.csv
```

This produces two CSV files:

- `pht_trace.csv`: full driver/load trace, written to stdout.
- `ysyx_22050058_pht_module_connections.csv`: module-boundary connections.

`-module` is a module definition name, not an instance name. For:

```verilog
ysyx_22050058_pht ysyx_22050058_pht_u0 (...);
```

use:

```bash
-module ysyx_22050058_pht
```

not:

```bash
-module ysyx_22050058_pht_u0
```

Internally the scripts use `npi_find_inst_with_def_wildcard` to find every
instance whose definition name matches `-module`.

## Files

| File | Purpose |
| --- | --- |
| `npi_trace.sh` | Main trace entry point. Runs Verdi in batch mode and emits the full trace CSV to stdout. |
| `npi_port_trace.tcl` | Core NPI script. Finds module instances, ports, directions, high/low connections, drivers, and loads. |
| `trace_and_filter.sh` | Runs a trace, finds instances of another module, and filters rows related to those instances. |
| `npi_find_instances.tcl` | Helper Tcl script used by `trace_and_filter.sh` to list instances of a module definition. |
| `filter_trace.py` | Filters and merges CSV output, and splits results per traced instance. |
| `npi_port_trace.cpp` | Older C++ version. The Tcl flow is the current recommended flow. |
| `Makefile` | Build file for the older C++ version. |

## Basic Trace

Trace one module definition:

```bash
cd /mnt/hgfs/VMshare-2/CPU_CORE/ysyx/npc/csrc/verdi_npi_port_trace

./npi_trace.sh \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -module ysyx_22050058_pht \
  > pht_trace.csv
```

Generated files:

```text
pht_trace.csv
ysyx_22050058_pht_module_connections.csv
```

Trace selected ports:

```bash
./npi_trace.sh \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -module ysyx_22050058_pht \
  -ports clk,rst,we,waddr,wdata \
  > pht_write_ports.csv
```

`-ports` takes port names from the module definition, not connected net names.

Choose the module-boundary CSV name:

```bash
./npi_trace.sh \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -module ysyx_22050058_pht \
  -module-out pht_module_only.csv \
  > pht_trace.csv
```

## CSV Outputs

### Full Trace CSV

Columns:

```csv
inst_full_name,port_name,role,signal_full_name
```

This uses trace APIs with module pass-through enabled. It follows driver/load
paths through module boundaries and internal Verdi nodes. You may see names such
as:

```text
Always0
SigOp7
Combo
RegCombo
ComboMemory
_ExprInst__
```

These are normal Verdi/KDB internal nodes.

### Module-Boundary CSV

Columns:

```csv
inst_full_name,port_name,role,module_signal_full_name
```

This uses trace APIs with module pass-through disabled and keeps readable module
boundary endpoints. It is better for answering “what does this port connect to
at the module boundary?”

Example:

```csv
...,we,driver,ysyx_22050058_gshare_u0.gshare_wepht_i
...,waddr,driver,ysyx_22050058_gshare_u0.bpu_fixbhr_i[12:0]
...,wdata,driver,ysyx_22050058_gshare_u0.gshare_fixpht_i[1:0]
```

Self-port driver endpoints are filtered from driver output. Constant drivers are
kept and printed as `Const:<value>`, for example:

```csv
...,CEN,driver,Const:'b1
```

## Filter By Connected Module

In `trace_and_filter.sh`, `-keywords` is a legacy option name. It does not mean
"search these text keywords in the CSV" anymore.

Current meaning:

- `-module <target_module>`: the module definition whose ports are traced.
- `-keywords <filter_module>`: one module definition name used as the source
  filter.

The script first asks Verdi to find every instance of `<filter_module>`, then
keeps rows where the traced port's driver/load endpoint belongs to one of those
instances. Comma-separated keyword lists are rejected.

Example: trace `ysyx_22050058_pht`, and keep rows related to
`ysyx_22050058_gshare` instances:

```bash
./trace_and_filter.sh \
  -module ysyx_22050058_pht \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -keywords ysyx_22050058_gshare \
  -output pht_from_gshare.csv
```

The script generates:

```text
ysyx_22050058_pht_full.csv
ysyx_22050058_pht_module_connections.csv
ysyx_22050058_pht_ysyx_22050058_gshare_instances.txt
pht_from_gshare_boundary.csv
pht_from_gshare_full_owner.csv
pht_from_gshare.csv
```

The filtering has two inputs:

- `pht_from_gshare_boundary.csv`: rows from
  `ysyx_22050058_pht_module_connections.csv`. This keeps direct module-boundary
  connections such as `we`, `waddr`, and `wdata`.
- `pht_from_gshare_full_owner.csv`: rows from `ysyx_22050058_pht_full.csv` whose
  full-trace endpoint is owned by a `ysyx_22050058_gshare` instance. This keeps
  readable logic produced inside that instance, for example `raddr1/raddr2`
  through `SigOp`.

The final `pht_from_gshare.csv` is the de-duplicated merge of those two files.

Ownership is name-based. A row is kept when `signal_full_name` or normalized
`module_signal_full_name` is:

- exactly the filter instance path;
- a direct signal under the filter instance, such as
  `...ysyx_22050058_gshare_u0.gshare_wepht_i`;
- Verdi logic generated directly in the filter instance, such as
  `...ysyx_22050058_gshare_u0.ysyx_22050058_gshare/Always0:...`.

Rows containing `_ExprInst__` are not included in the filtered output. Child
instance internals such as:

```text
ysyx_22050058_gshare_u0.ysyx_22050058_pht_u0.ysyx_22050058_pht(@1)/...
```

are also excluded, because they belong to a child instance inside the filter
module, not to the filter module instance boundary itself.

`filter_trace.py` still has a low-level `--keywords` text-search mode for
manual CSV debugging, but `trace_and_filter.sh -keywords` does not use that
mode.

## Per-Instance Split

If `-module` has multiple instances, `trace_and_filter.sh` also writes one CSV
per traced instance:

```text
<output_basename>__<inst_full_name>.csv
```

Example:

```bash
./trace_and_filter.sh \
  -module S013HD1P_X32Y2D128_BW \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -keywords S013HD1P_X32Y2D128_BW \
  -output s013_from_self.csv
```

If 12 SRAM instances are found, 12 per-instance CSV files are generated.

## Validation Examples

### Constant Driver

```bash
./npi_trace.sh \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -module S013HD1P_X32Y2D128_BW \
  -ports CEN \
  -module-out s013_cen_module.csv \
  > s013_cen.csv

grep -n 'Const:' s013_cen.csv
grep -n 'Const:' s013_cen_module.csv
```

Expected: `Const:'b1` appears as a driver.

### Same-Parent Module Connection

`ysyx_22050058_gshare` and `ysyx_22050058_btb` are both instantiated by
`ysyx_22050058_bpu`.

```bash
./trace_and_filter.sh \
  -module ysyx_22050058_gshare \
  -lib /tmp/npc_build/simv.daidir/kdb.elab++ \
  -keywords ysyx_22050058_btb \
  -output gshare_from_btb.csv
```

Expected rows include:

```csv
gshare_btbop_i,driver,...ysyx_22050058_btb_u0.btb_op_o[2:0]
gshare_btbhit_i,driver,...ysyx_22050058_btb_u0.btb_hit1_o
gshare_btbhit_i,driver,...ysyx_22050058_btb_u0.btb_hit2_o
```

## Cleanup

Generated files can be removed with:

```bash
rm -f *.csv *.err *.out *_instances.txt
rm -rf novas.conf novas.rc verdiLog
```

Do not remove these tool files:

```text
filter_trace.py
Makefile
npi_find_instances.tcl
npi_port_trace.cpp
npi_port_trace.tcl
npi_trace.sh
README.md
trace_and_filter.sh
```

## Notes

- The recommended path is `-lib <kdb.elab++>`.
- CSV output is a textual representation of NPI trace results, not a canonical
  netlist database.
- Verdi internal node names may vary across versions.
- Complex expression ports may require full-trace rows to recover readable
  upstream logic; module-boundary rows alone may stop at expression boundaries.
